## 4. Состояние репозитория и деплоя — вывод от 12.09.2026

### Проверено и работает — не трогать

Конвейер: **push в `main` → GitHub Actions → свежая сборка из `src/` + `public/` → Pages**.

- Подтверждено практикой: несколько пушей подряд, Actions срабатывает, прод обновляется.
- `dist/` в git на прод **не влияет** — workflow всегда собирает заново из исходников.
- Правки в `public/me/` (визитка) подхватываются сборкой напрямую: Vite копирует `public/` в артефакт как есть.

### Что лежит «не в порядке», но безвредно

| Объект | Фактическое состояние | Влияние на прод | Срочность |
|--------|----------------------|-----------------|-----------|
| Ветка `gh-pages` | не обновлялась с июня 2026 | нулевое — прод отдаёт контент из сборки `main` | удалять незачем |
| `dist/` в git | отслеживается 16 файлов; в `.gitignore` закомментарен ложный текст «dist/ is committed to gh-pages branch» | нулевое | шум в `git status`, не более |
| Source в Settings → Pages | в UI подсвечено `gh-pages / (root)` | фактически публикует workflow | **не переключать** |

Последняя строка — намеренное решение: источник не переключать и ветку не удалять, пока всё работает. Риск нулевой пользы против риска уронить рабочий деплой.

### Триггеры: когда наведение порядка действительно нужно

Порядок нужен не «когда-нибудь» и не ради чистоты, а по конкретным симптомам:

1. **Главный сигнал.** Запушены код + изменённый `dist/`, и при этом прод не совпадает с тем, что в репозитории → начинается поиск причины. Тогда нужно первым делом проверить, **успешен ли последний run Actions**, а не анализировать отличия в `dist/`. Изменения в `dist/` — это ложный след: они выглядят как причина, но на прод не влияют.
2. **Шум мешает работать:** правки в `dist/` постоянно попадают в коммиты, `git stash` / `git checkout` задевают собранные ассеты, возникают конфликты при merges на хеш-именах (`index-<hash>.js`). Сейчас этого нет.
3. **Меняется способ публикации** (другой хостинг, ручной деплой) — тогда `dist/` надо привести в соответствие или удалить осознанно.

### Смысл уборки (зачем, когда пробьёт час)

Убрать `dist/` из отслеживания нужно не для красоты, а чтобы:
- `git status` показывал только реальные изменения исходников;
- пропал сам соблазн коммитить собранное и искать причину расхождений не там.

Процедура (один коммит, на деплой не влияет):
```bash
git rm -r --cached dist          # убрать из индекса, файлы останутся на диске
echo "dist/" >> .gitignore       # плюс поправить ложный комментарий про gh-pages в .gitignore
git commit -m "Stop tracking dist/ build output"
git push
```

### Визитка — разделение режимов (архитектура)

Механизм `?owner=1` — два взгляда на одну страницу:

```
seezam.online/me/              → визитка без инструментов (получатель)
seezam.online/me/?owner=1      → визитка + QR + копирование ссылки (владелец)
```

- Один HTML-файл, нулевая серверная логика

- При `isOwner`: показывается `#qr-block` (QR + кнопка копирования) и `#owner-tag` ("режим владельца")
- QR всегда кодирует "чистую" ссылку (без `?owner=1`) — чтобы сканирующие попадали в режим получателя
- Копирование ссылки — тоже чистая ссылка (без параметров)
- См. также: «Визитка — разделение режимов (обновлено 22.09.2026)» ниже — там зафиксировано решение с двумя манифестами

### Визитка — разделение режимов (обновлено 22.09.2026)

**Режим определяется ТОЛЬКО по `?owner=1` в URL:**

```
seezam.online/me/              → визитка без инструментов (получатель)
seezam.online/me/?owner=1      → визитка + QR + копирование ссылки (владелец)
```

- `localStorage` и `sessionStorage` для определения режима **убраны** (коммит `d908e28` — первая попытка; 22.09.2026 — окончательно) — они «прилипали» ко всему браузеру и получатель видел QR владельца
- `sessionStorage` для `vcard_install_shown` (модалка установки) — оставлен, это другой ключ, он не течёт
- **Два манифеста с динамическим переключением** (22.09.2026):
  - `public/me/manifest.json` — `start_url: "./"` (без параметров) — для получателя
  - `public/me/manifest-owner.json` — `start_url: "./?owner=1"` — для владельца
  - Переключение в `<head>` через JS: если `?owner=1` → `manifest-owner.json`, иначе `manifest.json`
  - `id` в обоих манифестах одинаковый: `"/me/"` — чтобы браузер воспринимал это как одно PWA, а не два разных
- **PWA-ярлык владельца открывает режим владельца** (с QR) — `start_url` в `manifest-owner.json` содержит `?owner=1`
- **PWA-ярлык получателя открывает режим получателя** (без QR) — `start_url` в `manifest.json` без параметров
- QR всегда кодирует «чистую» ссылку (без `?owner=1`) — чтобы сканирующие попадали в режим получателя
- Копирование ссылки — тоже чистая ссылка (без параметров)
- После изменения манифеста нужно удалить старую иконку с экрана и установить заново — Chrome кэширует `start_url` установленного PWA

### Проблема кэширования PWA

- Chrome PWA кэширует `start_url` из манифеста при установке ярлыка — старая иконка будет открывать старый `start_url` даже после деплоя новых манифестов
- Решение (22.09.2026): удалить старую иконку с экрана → открыть `?owner=1` в браузере → установить заново — тогда подхватится новый `manifest-owner.json`
- На новых устройствах кеша нет — всё работает корректно
- Для избежания кэширования в будущем можно добавить query-строку к файлам (`index.html?v=2`) — но это усложнит сборку
